# 迁移新增哈希清理

2026-10-30，按本人要求删除迁移实现和验收中自建的哈希机制。
已提交并部署实际实例 `6ae4ada0`；social schema 10→11，提示协议 `social-judge-v4`。

## 当前实现

| 原用途 | 现在的做法 |
| --- | --- |
| 消息内容哈希和编辑识别 | 现有消息 ID/seq 加递增 revision；编辑即加一，包括正文未变的引用/媒体编辑 |
| 判断输入哈希和去重 | 明确的 batch_id、冻结的输入事实直接比较；本地记录摘要长度、消息 revision，不复制完整聊天 |
| provider/提示/配置签名 | provider 配置在内存直接比较；普通设置和提示原值本地比较后分配递增 revision，不落 provider 凭据 |
| scope 与人格哈希 | 小整数版本；角色文本单独比较，在下一回合更新，不中断本轮角色修改确认 |
| 记忆抑制哈希 | 原消息 ID 和规范化内容原值；删除、纠错、清空和过期继续有效 |
| 媒体缓存哈希文件名 | 群/话题 ID 与 Telegram 文件 unique_id；拒绝路径字符，保留缓存预算与重启复用 |
| 发布包 SHA256SUMS / 镜像 ID 指纹 | 删除自建校验和及镜像 ID 比较；保留文件清单、提交标签、架构、安装冒烟、健康检查、备份和失败回滚 |
| 验收文件指纹 | 直接比较配置、角色、消息、记忆和水位原值；验收不计算哈希 |

Git 提交号、Docker 自身管理的对象标识及 Telegram 原生文件标识仍由各自系统提供；
本迁移不再自行计算或建立哈希层。普通助手原有的鉴权、工具权限和沙箱保持原行为。

## 模型输入与数据升级

中间模型只收到对话事实；batch_id、scope、version、expires、quiet_due、total_due 和
消息 revision 均留在代码层。模型仍能看到当前时间、消息时间与等待意图的实际期限。
复用上一批 21 个合成语境，实际中间模型全部符合预期；输入 Token 合计
28207→26392，进一步减少 6.4%。输出加输入共 27568 Token。
这是有限样例的调用记录，未据此声称实际群聊延迟下降相同幅度。

schema 11 删除 judge_batches 的 signature/input_hash 列和旧唯一键，
删除本地 input_meta 中的 content_hash；消息增加 revision，派生版本替换为短版本号。
旧未完成中间调用作废，仍有效的待判消息保留；已完成的决定不重放，历史调用量不退回。
原消息、主 seen/read 水位、记忆与证据、角色及配置保留。

旧记忆抑制表的不可逆键不能还原成全部原文。对于确有旧抑制记录的作用域，
保留已有 inactive 记忆的原值，并建立旧证据水位，防止用旧消息重新学习被退役的内容；
后续需新证据继续学习。实际实例该表为空，本次没有作用域需要新增此水位。
旧哈希媒体缓存属于可重新下载的临时数据，启动时清除旧命名文件，随后使用原生标识缓存。

已在实际数据库临时副本验证 schema 10→11、运行初始化、SQLite 完整性与外键：
102 条消息、3 个 scope 水位、3 条记忆及证据直接比较通过；没有改动实际实例。
上线后按自动备份中的原值再次核对，不调用旧指纹脚本。

旧发布包不再要求 SHA256SUMS，更新后的管线可以读取旧元数据以恢复原版本。
回滚到 schema 10 程序仍需同时恢复该版本对应的数据备份。
