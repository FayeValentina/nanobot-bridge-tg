# Telegram 群流式回复缓慢：排查与修复

2026-10-28，本人实际实例的群回复生成很快，但流式显示持续缓慢。

## 证据与原因

排查时实际实例仍运行 `fbfe7a3c`，使用 `deepseek-flash`，Telegram streaming 开启，
`streamEditInterval` 为 0.6 秒，richMessages 关闭，群消息经过普通流式回复路径。
最新相关日志显示：05:13:56 开始处理，05:13:57 已生成回复；随后在 05:14:23、05:15:24
分别出现 `Flood Control ... retrying in 34.0s`。这里使用日志显示的时间，不另作时区推断。
这次主要延迟发生在 Telegram 出站阶段，模型生成约一秒，并非同等长度的模型计算等待。

旧实现的 `last_edit` 记录 API 调用开始时间。若网络调用本身超过编辑间隔，
返回时下一条已排队的 delta 又满足编辑条件，从而把旧片段逐个提交给 Telegram。
ChannelManager 的全局队列合并不能消除已经进入每个目标 FIFO 的片段。
过密的群内编辑进一步触发限流；中间预览使用通用重试器等待 34 秒，会把最终完整回复堵在旧预览之后。

Telegram [官方 FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)
说明了单聊天和群的消息频率限制；本次编辑触发限流由实际运行日志确认，不能把
“0.6 秒更新”理解为对群编辑频率的保证。

## 修复

- 每次预览操作完成后才记录时间，网络等待时间不再提前消耗编辑间隔。
- 群/频道的流式中间编辑间隔至少 3.2 秒；首段及时显示，生成结束时直接提交完整文本，
  不为了预览节流而额外等待 3.2 秒。
- 中间预览收到 429 时记录 Retry-After 截止时间并继续积累文字，避免在每个旧片段上重试等待。
  最终完整回复只在必要时等平台冷却，再使用已有可靠发送/重试路径。
- 中间预览网络失败不重新执行已接收的 delta，防止文字重复；最终完整文本继续负责可靠收尾。
- 不改变本人现有模型、Bot Token、群权限或仿真开关。群预览保持流式，私聊 rich draft 原有策略保留。

## 验证

新增五项可控时钟回归覆盖慢初始发送、慢编辑、群节流、34 秒限流及预览超时。
在修复前五项均能复现问题；修复后 Telegram 相关测试 145 项通过，Ruff 与严格类型检查通过。
新文件已纳入本机发布管线的检查范围。

使用同一套本地替身对比已提交旧实现与修复后实现：40 个排队片段，每次假定 API 调用耗时 2 秒。

| 指标 | 旧实现 | 修复后 |
| --- | --- | --- |
| Telegram API 请求次数 | 42 | 2 |
| 模拟出站耗时 | 84 秒 | 4 秒 |
| 最终完整文字 | 保留 | 保留 |

这是可控时钟的模拟结果，不是实际 Telegram 网络测速，也不承诺真实回复固定为 4 秒。
Telegram 若已经限流，仍需遵守它返回的冷却时间；本修复减少造成后续限流的请求放大。
真实使用效果以部署后本人继续 @ 机器人的表现和新日志为准。
