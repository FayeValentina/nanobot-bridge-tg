## 状态与参与方式

每个群/话题独立保存 `observing`、`active`、`waiting`、`sleeping`、`paused`。
执行中的 WakeJob 与行为状态分开保存：等待/潜水可以先持久化，结束当前模型回合，
由消息或期限决定是否再唤醒，不占住 Agent 会话锁。

| 状态/事件 | 行为 |
| --- | --- |
| observing | 普通消息只记录；按已配置的点名、昵称、关键词、成员或普通消息条件生成候选 |
| active | 通过现有 AgentLoop 和会话锁执行；新触发在 SQLite 中合并，不直接启动第二个回合 |
| waiting | 关注新消息；期限到达时恢复观察，按工具参数决定是否产生一次超时关注 |
| sleeping | 忽略普通参与条件，丢弃待处理的普通触发；@/回复和管理员配置的昵称可打断 |
| paused | 保留观察记录，拒绝唤醒和工具发送，取消旧定时器及尚未发送的动作 |

触发优先级为点名/回复、昵称、关键词、指定成员、普通消息、超时。
默认仍只有 @/回复唤醒；昵称、关键词和普通消息参与需要配置，或由已获准回合设置关注条件。
Bot 消息可以记录，不能生成参与触发，也不推进可产生超时关注的新成员消息水位。

短窗口以第一条触发为起点，默认 1.5 秒，连续消息不会无限延长它。窗口内只保留一个
待调度记录和最新关联 seq，快照包含窗口内的普通消息。观察、更新去重及候选唤醒在同一
事务提交，写入失败不会留下“记录了消息但丢失唤醒”的半完成状态。

忙时触发只有一个合并候选。当前回合结束后重新检查时效、预算和冷却，再决定是否投递。
若 `social_read_messages` 已将该触发实际送入当前 provider 请求，则曝光 hook 将它归入
当前回合完成，避免再跑一轮；仅返回工具结果尚不足以消费该触发，未读仍需显式确认。

## 工具与静默

在 M1 四个工具之外增加：

| 工具 | 参数和边界 |
| --- | --- |
| social_wait | `seconds` 必填；`sleeping` 默认 false；`on_timeout` 默认 false。持久化决定并立即结束回合，必须作为最后一个动作 |
| social_set_wake | 当前群/话题的 `keywords`、`senders`、`on_messages`；不接受目标群、角色、权限或预算参数 |

`social_wait` 不通过等待工具内部 sleep 占住回合，也不额外请求模型生成结束语。
成功后拒绝本回合后续 social 操作；已经在平台处理中的发送不能撤回。
通用核心只增加 `AgentHookContext.end_turn`，runner 在工具结果和检查点写入后处理它。
状态和调度仍在 Telegram social 模块中，普通私聊的回复流程保持原行为。

超时关注是一次性的：只有明确设置 `on_timeout: true` 才会生成；同一段新成员消息最多
消费一次超时关注，模型反复设置相同等待不能产生持续轮询。期限错过超过 120 秒直接回到
观察状态，不在长时间停机后生成新的过期话题。一般定时主动机会与安静时段仍属于 M4。

`social_get_state` 返回实际状态、等待期限、模型关注条件、剩余唤醒次数、剩余发送尝试
次数和发送冷却期限。模型设置的关注条件只在当前配置版本有效；管理员可通过
`allowAmbientWake: false` 禁止模型修改关注条件。它不能改变群/话题授权、观察成员、
人格、暂停状态、硬预算或时长上限。

## 调度、预算与恢复

`social.sqlite3` 仍是唯一持久队列。`SocialScheduler` 是通道生命周期拥有的单个事件驱动
worker，只等待最近期限或配置/消息/回合完成事件，不持有 Agent 会话锁。
启动恢复发生在 Telegram 接收新更新之前；停止通道时等待 worker 退出。

唤醒从 `scheduled` 变成 `queued` 才进入进程内 MessageBus，执行入口再原子认领为
`running`；完成、失败、过期、取消都有明确状态。入队不是模型完成，也不是公开发送成功。
同一 scope 的在途唤醒阻止第二份候选投递，120 秒租约避免中断遗留永久繁忙。

每小时唤醒次数按投递尝试记录，不按观察消息数累计；多个消息合并只记一次。
冷却或小时预算未恢复时，候选保留原有效期并重排；恢复前过期则丢弃候选，消息仍未读。
发送尝试有独立滚动日志，429 的每次实际尝试都计入预算；原动作跨过小时边界不会漏掉
较新的重试。调度、授权检查和计数不调用模型。

重启后每个 scope 最多保留一个仍有效的事件候选，重新检查冷却和小时预算。
等待决定已经落盘但 runner 尚未收尾时，将旧运行视为已经让出，不重放旧回合。
配置变化、角色变化、撤权、全局关闭或暂停会取消旧版本任务及未发送动作。
不透明的 provider 恢复状态仍遵循 M1 的清除策略，群历史与人格/记忆隔离继续保留。

## 发送、分条与平台重试

单条 `social_send` 继续直接取得平台回执。额外传 `parts` 可附加最多两条短文字，合计
最多三条；每条独立验证长度、预算、引用和作用域，按发送冷却串行投递。
工具返回各 action 的 `queued`，不提前声称 sent。每条收到 Telegram message_id 后
才写 sent 并加入观察记录。总发送预算不足以容纳整组时不入队。

同回合重复发送相同文字或相同分条组返回已有动作结果，不重新投递。分条中一条失败或
结果未知会取消后续分条，已确认的前几条不会重发；各子动作可以分别检查实际状态。
所有动作都保留原 thread_id 和已观察的引用对象，无法引用时不降级到其他话题。

Telegram 明确返回 429 时，转成与 SDK 解耦的 `SocialRateLimitError`，按 Retry-After
持久化重排同一 action，最多三次实际尝试，并受原唤醒期限和小时发送预算限制。
后续分条必须等待前条确认，重试不启动模型回合。

超时、断网或取消导致结果不明时仍记 `unknown`，不自动重发。
进程重启后，在途/等待重试的已尝试动作也保守转为 unknown；未尝试的分条取消，
不能恢复后整组补发。未知文字的跨回合重复保护继续保留 24 小时。

## 配置与数据库版本

配置仍通过 `channels.telegram.social` 和现有 Telegram 设置页 JSON 字段维护，
新字段使用相同的 Pydantic 校验、camelCase 输入和输出契约，无额外前端枚举。

```json
{
  "enabled": false,
  "coalesceSeconds": 1.5,
  "cooldownSeconds": 10,
  "sendCooldownSeconds": 2,
  "maxWaitSeconds": 3600,
  "maxRequestsPerHour": 12,
  "maxSendsPerHour": 6,
  "scopes": [
    {
      "chatId": -1001234567890,
      "threadId": 42,
      "roleId": "guest",
      "observeFrom": ["*"],
      "paused": false,
      "nicknames": ["小客人"],
      "wakeKeywords": [],
      "wakeSenders": [],
      "wakeOnMessages": false,
      "allowAmbientWake": true
    }
  ]
}
```

群号仅为示例。角色目录和精确话题授权继续按 [M1 说明](M1_IMPLEMENTATION.md) 配置。
合并窗口允许 0–10 秒；回合冷却 0–300 秒；发送冷却 0–60 秒；单次等待上限配置
允许 1–86400 秒。模型参数仍必须小于管理员配置的等待上限。

SQLite 从 schema 1 事务升级到 schema 2，保留消息、未读水位、回执与原记录，补充状态、
期限、候选原因、分条关联和滚动尝试日志。未知版本或损坏库继续拒绝启动，不重建空库。
schema 2 不能直接交给旧版 M1 读取；降级应连同发布前的数据备份恢复。
本次只对临时数据库验证迁移，生产数据仍未升级；部署与备份恢复仍按本机管线执行。
