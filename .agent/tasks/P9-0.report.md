### 1.2 边界情形

| 情形 | 一次注入后的行为 | 是否额外处理 |
|---|---|---|
| 无 `consolidate_history`、无 `ContextCompactionState` | `from_transcript()` 返回 `None`；runner 直接使用已恢复的原始 transcript。第 2 次起没有块。`context_governance.py:147–149`、`runner.py:444–448` | **需要**。例如对无 H 路径保留同一份临时内容到 finally，再恢复；不能每轮重新 build 更新状态。 |

压缩实测：强制在第 2 次请求前压缩，摘要 stub 不复制 memory：


还有一个底层边界：若 `TranscriptInput.current_message=None`，hook 修改的是已经进入初始 H 的历史对象，修改不会进入 unsent delta。临时 history-only 探针结果为 **0/0/0/0**。正常 social inbound 的 `_build_transcript_input()` 会提供 `ctx.msg.content`（`loop.py:658–667`），因此不是本案例的常规路径，但直接 runner 调用不能假定一定有新 user delta。

曝光登记依据：

- `db/views.py:14–16` 同时要求 `view_id` 和对应 `view_end`。
- `store.py:183–207` 只登记真正曝光的 view，推进连续 seen 水位，并接纳已显示的 busy-time trigger。
- 一次注入不改变 snapshot 内容，也不改变 `context.model_messages` 的生成顺序。

### 1.3 摘要污染的最小排除办法

当前污染路径已由强制压缩验证：

```text
H → consolidation_prefix → summarize_transcript()
```

`context_governance.py:538–544` 传入 H；`agent/memory.py:1115–1119` 只排除 system，没有排除 social 临时块。

最小办法：

1. hook 保存 `append_runtime_context()` 返回的精确 marker，不能继续丢弃。
2. marker 随模型侧消息进入 H。
3. 摘要前在深拷贝上，按 marker 精确移除 **`telegram_social_memory`／`telegram_autonomous_work`**；同时清理传给 archiver 的 `source_messages` 和 `history`。
4. 保持原始 transcript、真正发送的 `model_messages` 和 view 首尾标记不变。

现成能力在 `runtime_context.py:120–145,148–181`，分别支持字符串 suffix 和多模态末尾 blocks，无需哈希或文本猜测。

这涉及**通用 agent 的摘要边界**，但可限定为带明确 social 临时 marker 的消息；没有该 marker 的普通会话应保持原样。不能直接删除所有 runtime context：普通 explicit skills、引用等具有不同生命周期。

另须注意 `summarize_provider_compaction()` 会传入原生 provider state（`agent/memory.py:1145–1163`）；只清理可见消息不能清除已进入不透明 state 的块。线上本案例没有该 state。

1. **T1 的“只加 iteration 判断”不完整。** 无 H 会丢块；压缩后也会丢。应先定同一份初始块在无 H／压缩后的生命周期，再派实施任务。不能重新每轮 build 补状态。
