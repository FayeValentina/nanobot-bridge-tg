### 1.2 live memory 是否叠加：确定会

顺序如下：

```text
before_iteration：
  恢复原始 transcript 上一次的 target
  向最新 user/tool 注入 Mₙ

发送：
  请求 = deepcopy(accepted H) + deepcopy(原始增量)

收到响应：
  accepted H = deepcopy(本次模型输入)

after_iteration：
  只恢复原始 transcript 的 target
  accepted H 中的深拷贝不受影响
```

直接依据：

- hook 保存目标对象和原始内容，并在该对象上追加上下文：[hook.py:38](/home/ubuntu/nanobot-bridge-tg/nanobot/channels/telegram/social/hook.py:38)、[hook.py:44](/home/ubuntu/nanobot-bridge-tg/nanobot/channels/telegram/social/hook.py:44)。
- `append_runtime_context()` 返回拼接后的新内容；hook 丢弃了返回的移除 marker：[runtime_context.py:120](/home/ubuntu/nanobot-bridge-tg/nanobot/runtime_context.py:120)、[hook.py:68](/home/ubuntu/nanobot-bridge-tg/nanobot/channels/telegram/social/hook.py:68)。
- H 的读取和写入均使用深拷贝：[context_governance.py:166](/home/ubuntu/nanobot-bridge-tg/nanobot/agent/context_governance.py:166)、[context_governance.py:181](/home/ubuntu/nanobot-bridge-tg/nanobot/agent/context_governance.py:181)。
- runner 在调用 `after_iteration` 恢复原始对象之前，已经执行 `accept_request()`：[runner.py:459](/home/ubuntu/nanobot-bridge-tg/nanobot/agent/runner.py:459)。

因此，第二轮实际请求保留第一轮 user 中的 M₁，并在新 tool 中加入 M₂；第三、四轮继续累积。即使 M₁～M₃ 内容相同，也会发送多份。

正常返回的原始 transcript 中没有这些块，复现所有 `raw_live_blocks` 均为零。这解释了**会话文件看起来干净，但 turn 内请求膨胀**。

## 4. 根因与修复方案

### 4.1 问题 1：临时注入进入 accepted/H，恢复没有覆盖深拷贝

**确定根因。** 代码顺序、四次真实请求记录和关闭 H 的对照结果一致。

方案 A：为 social 临时块保留精确移除标记，在构造下一次请求及摘要输入时排除旧临时块，再加入当前一份。

- 涉及 `SocialExposureHook`、`ContextCompactionState.request_messages()` 及摘要输入处理。
- 复现中，第二、三、四次请求分别可少约 **7.17k、14.34k、21.50k** cl100k token；线上量级约 **5.6k、11.2k、16.8k**。
- 不应泛化删除所有 runtime context：其他来源可能具有持久重放语义。
- 风险：改写旧请求前缀会降低 provider 前缀缓存命中；Responses 私有状态还需要明确失效规则。
- `context.model_messages` 必须保留真正发送的版本供 `note_seen()` 使用。不能删掉 snapshot 的 `view_id/view_end`，不能改变原始 transcript 边界或 D4 历史。

方案 B：一个 turn 只注入一次完整块；发生相关状态变化时仅追加小型更新。

- 可保持 append-only 前缀及较好的缓存命中，消除反复加入完整块的主要增长。
- 风险：record 后的新记忆、已确认发送和活动变化需要明确更新规则，否则后续迭代读取旧状态。
- 两方案都应明确：临时快照是否进入摘要。仅恢复原始 transcript 不足以解决摘要污染。

这是**通用 agent 层的状态契约问题，由 social 动态注入触发**。普通会话中采用相同临时修改方式的 hook 也可能受影响。

### 4.2 问题 2 的已确认来源之一：普通聊天无条件携带五条完整活动笔记

- 风险：普通聊天对旧活动的细节回忆需要一次工具读取。

- 风险：paused 活动的自然续接、completed 活动的相关回忆可能减少。

两者均为 **social 专属上下文策略**。应先解决副本累积，再评估单份大小，避免把两项收益重复计算。
