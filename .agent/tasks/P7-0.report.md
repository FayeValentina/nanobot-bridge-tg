### 1.6 显式选择性等待的实际表示及 B/C 歧义

**存储与入口**

- `social_set_wake` 将 keywords、senders、on_messages、on_question、sleep_interrupts、coalesce_seconds、expires_at、one_shot 保存成 `scopes.wake_config` JSON；无任何条件则清 `{}`。不保存模型原话 description。依据：`S/waiting.py:127–166`；`nanobot/config/schema.py:152–174`。
- `social_wait` 当前只支持 duration、sleeping、on_timeout、purpose、quiet_seconds；**没有** `until_condition` 或自然语言条件字段。依据：`nanobot/agent/tools/telegram_social.py:165–184`；`S/waiting.py:79–125`。
- `dialogue_waits` 保存 scope、purpose、started、quiet_seconds、quiet_due、total_due、after_seq、source_seq、on_timeout、sleep_seconds、condition_expires、sleep_until；不保存 keywords/senders/on_question。依据：`S/db/wakes.py:400–403`。
- `dialogue_jobs` 是 wake 的 continuation 元数据：job、purpose、quiet_seconds、quiet_due、total_due、after_seq、source_seq；可被后来的等待覆盖，不是完整历史。依据：`S/db/wakes.py:164–166,469–472`。
- `conditions()` 的 dynamic 标志最初只是 `raw!="{}"`；过期清配置。`intent()` 又收窄为 raw非空且存在 keywords/senders/**on_messages**/on_question。依据：`S/waiting.py:37–43`；`S/judge_runtime.py:93–104`。

**各状态当前收到的 intent**

| 状态 | intent 内容 |
|---|---|
| observing/active，无临时条件、无 dialogue_wait | `null`；scope 常驻偏好另放 participation |
| 普通 reply/messages wait，无临时条件 | purpose对应等待；description=`Waiting for a relevant conversation continuation, including photos and short answers; not only questions.`；JSON尾部 waiting_for_messages=true、waiting_for_questions=false；keywords/senders空；one_shot=false |
| 旧式 waiting/sleeping，无 dialogue_wait、无条件 | purpose=null；description仍是普通 continuation；until=scope.wake_at；infinite=scope.wait_infinite；keywords/senders空；one_shot=false |
| 有临时 keywords/senders/on_question，非 observe | description=`An explicit wait is selective; ordinary unrelated messages need not interrupt it. Clear calls remain reachable.`；带临时关键词/成员；questions/messages布尔嵌在 description JSON；携带 expires、one_shot |
| 只有临时 on_messages=true | 也被当前代码称为 selective；keywords/senders空，description里 waiting_for_messages=true |
| purpose=observe 的睡前观察 | description=`Background observation before sleep, not a selective wait for questions.`；不称为 selective，questions=false、messages=false；但有 dynamic 时仍会携带 keywords/senders、condition_expires、one_shot |
| 普通 wait 加仅 coalesce/sleep_interrupts 的非空旧配置 | intent() 将 dynamic收窄为false，因此作为普通 continuation，不携带临时 expires/one_shot |

以上生成逻辑统一见 `S/judge_runtime.py:90–119`。until 优先取 dialogue_wait.total_due，否则 scope.wake_at；interrupt_policy 是 `{operator,temporary}` 的 **JSON字符串**。

**能否只靠字段实现 B/C？**

能按持久化结构判定常规情形，但不能直接用 `JudgeIntent.keywords/senders`：`on_question/on_messages` 没有独立 DTO 字段，而是嵌在 description 中。应从未过期的 wake_config 原字段判定；无需模型识别“是否选择性等待”。依据：`S/judge_models.py:40–51`；`S/judge_runtime.py:110–118`。

需要决定的歧义：

| 情形 | 解释一 | 解释二及当前差异 |
|---|---|---|
| 仅 on_messages=true | 按 §5.1 字面“没有 keywords/senders/on_question”归 B | 当前 intent 称 selective，可理解为旧接口的显式等待；但不限制人/话题，C没有实际筛选条件 |
| sleep，无条件，sleep_interrupts 全false | §5.1明确归 B，新消息可唤醒 | SleepInterruptConfig docstring称 operator ceiling，容易被理解为禁止普通中断；当前只作为 judge 文本上下文，没有本地硬门槛 |
| sleep，有临时keywords/senders，operator对应 interrupt=false | 仍属 C，判断条件是否满足 | 若 operator ceiling有效，则满足条件仍可能不得打断；§5.1没说明是否保留此限制 |
| purpose=observe，同时有临时选择条件 | observe 是背景观察，按提示词第22行不当选择性等待，归 B | 原始 wake_config仍有条件，按§5.1表格会归 C；当前DTO还携带这些条件 |
| purpose=messages 且 condition_expires 非空 | 只是附带TTL；须看 wake_config 是否有选择条件，普通消息等待仍 B | 将非空 condition_expires误当选择性标记会错误进入C |
| dialogue_wait 过期而 wake_config仍有效 | 临时条件本身代表显式等待，继续C | 若要求“必须正在waiting/sleeping”，则归B；当前 observing/active 只要有dynamic仍生成 selective intent |
| 常驻 binding.wake_keywords/senders/on_question | participation，始终不能单独令其进入C | 若迁移把 effective() fallback值当临时条件，会收窄V3广泛准入 |
| 模型说“等小明回来”但只调用普通 social_wait | 现有持久化没有保存该原话，不能可靠恢复语义条件，归B | 从历史对话推断成C会引入额外语义识别，超出§5.1平台事实分流 |

condition_expires 的来源尤其不能当条件证明：messages wait 在 dynamic **或 infinite** 时可传 effective.expires_at；自动回复等待也可能带 dynamic expires。依据：`S/waiting.py:97–101,177–181`。

### 1.9 已曝光消息复用原 wake 与 B1-a

完整条件见 `S/db/judge.py:198–211`：

1. batch存在。
2. batch尚无handoff_job。
3. decision=wake。
4. judge_state存在同scope、同batch_id，防独立评估直接调度。
5. 查询同scope最近32条 wake，状态为 completed，或未过期running。
6. 对每个wake的turn_id查询当前scope.version下 `seen=1` 的views.seqs。
7. snapshot.new_seqs非空，且 **全部new_seqs和全部decision.source_seqs** 都包含在这个turn的shown集合。
8. 满足则只写handoff_job=旧wake.id；不新建wake。若 fulfills、one_shot、冻结condition_config仍等于当前配置，则清配置。

依赖表/方法：

- judge_batches、judge_state：批次归属、幂等、冻结条件。
- wakes：`recent_turns`，`S/db/wakes.py:460–461`。
- views：`shown_sequences`，仅当前version、已seen、指定turn；`S/db/views.py:24–29`。
- scopes：当前version与wake_config。

迁到Wakes所需语义输入：scope、批次全部新消息seq、目前的source_seqs、fulfills_intent、one_shot、待消费的条件原值；不再有source_seqs时，至少保留**整个批次new_seqs**，不能只拿最后trigger_seq证明整批曝光。普通新wake还需要trigger_seq、reason/admission、expires及保留的dialogue时限。依据：`S/db/judge.py:207–226`。

B1-a交互：

- `delivery._collect_new_messages`在本turn最新曝光seq之后发现非SELF消息，首次新发送抛PermissionError，附完整新snapshot；每scope每turn最多拦一次。依据：`S/delivery.py:65–81`。
- text/sticker发送及parts在幂等回执分支之后调用收取。依据：`S/delivery.py:58–63,130–134,177–183`。
- 新snapshot真正进入provider请求后，hook登记曝光；若wake已schedule，`admit_shown`收取进当前turn。依据：`S/hook.py:70–78`；`S/store.py:203–208`。

- 因此不能把“completed也可复用”删成“只检查当前running”；也不能先推进主read就当作已曝光，真正依据是views.seen。

## 4. selection（含 ValidationError 诊断）

### 4.1 ContextSelector.select 完整流程

**调用频率**

生产中只有 `SocialContextBuilder.build` 调用select，build由每次`before_iteration`调用。因此是**每次模型迭代进入select，但同turn最多一次LLM选择调用**，不是select函数每turn只执行一次。依据：`S/context.py:52–55`；`S/hook.py:44–57`；全仓搜索其他select调用均在 `T/test_social_selection.py`。

**输入与缓存**

1. 按scope加asyncio.Lock。读取该turn及未claim views，按最新created/rowid排序，选实际transcript含完整view标记的最新view；取末8条消息，并补同scope/当前revision的已学来图贴纸备注。依据：`S/selection.py:127–143,203–207`；`S/db/views.py:46–48`。
2. 缓存键`(scope,turn)`；TurnSelection保存source、scope.version、learning.config_revision、selected、status。OrderedDict最多100项，按插入先后淘汰；provider重配清整个cache。依据：`S/selection.py:68–74,111–121,207–223`。
3. 已缓存时，每次重新比较source、version、config_revision，检查所有source message revision及所有selected candidate当前值；全一致才返回旧选择。依据：`S/selection.py:209–214`。
4. 不一致则在内存recent详情写`reuse_status="changed_input_or_entry_returned_empty"`，返回空；不重选，不清旧cache，不另写expression_turns。依据：`S/selection.py:215–219`。
5. 首次先写内存cache；若SQLite已存在expression_turns，该turn返回空，防重启/淘汰买第二次调用。依据：`S/selection.py:220–225`。

**LLM前后检查**

- 调用前：enabled、provider、source非空；否则disabled_or_unavailable。候选pool为空不调模型，status保留empty。没有独立的调用前messages_current/current全量检查；这些检查主要在缓存重用及调用后。依据：`S/selection.py:231–238`。

### 4.2 动态 SQL、参数及仓储归属

完整生成逻辑位于 `S/selection.py:152–179`，其中核心SQL原样为：

```python
haystack = "lower(" + "||' '||".join(fields) + ")"
score = "+".join(f"(instr({haystack},?)>0)" for _ in needles) or "0"
partition = "intent_category" if kind != "sticker" else "substr(note,1,6)"
revision = "revision" if kind != "sticker" else "0 AS revision"

SELECT * FROM (
    SELECT id,{revision},{','.join(fields)},({score}) AS relevance,
           ROW_NUMBER() OVER (
               PARTITION BY {partition}
               ORDER BY updated DESC,id
           ) AS variety
    FROM {table}
    WHERE scope=? AND {condition}
)
ORDER BY relevance DESC,variety,id
LIMIT ?
```

完整替换项：

| kind/table | fields | condition | 参数顺序 | 所有者 |
|---|---|---|---|---|
| expression /expressions | situation,expression,tone,suitable,unsuitable,scene_tags,intent_category | `status IN ('available','usable')` | needles各项、scope、limit | ExpressionLibrary |
| jargon /jargon | term,aliases,local_meaning,public_meaning,usage,unsuitable,status,scene_tags,intent_category | `status IN ('understand_only','usable') AND (expires IS NULL OR expires>?)` | needles各项、scope、now、limit | JargonLibrary |
| sticker /stickers | note | `trim(note)<>''` | needles各项、scope、limit | `S/db/stickers.py` 的StickerLibrary |

expression/jargon的needles＝retrieval_terms+命中scene名；sticker的needles＝retrieval_terms+命中scene对应的中文提示词。score为每个needle的instr命中布尔值相加，无needle时为0。limit分别受expression_candidates/jargon_candidates/selection_sticker_candidates控制；若该类别最终选择数为0则不查询。依据：`S/selection.py:145–174`。

## 6. 疑点 / 需要编排者决定的事项

1. **实际observe变化规模超出“仅罕见私聊”的描述。** 副本8条observe全部会归B，主要是机器用量回执，占现存批次19.51%。它们不属于A平台保护；若要继续屏蔽，必须另行授权语义范围，不能偷偷加文本规则。依据：第2.2节8个主键；`social_judge.md:11`；设计`403–410`。

2. **失败黑话证据已被旧逻辑改变状态。** 历史文档的failed/cursor0与当前副本cancelled/scope_changed、cursor61冲突；当前代码允许scope/config变化取消failed，再重新批次处理。应保留实际行及历史文档差异，不能把迁移验收建立在“当前仍failed”的假设上。依据：`S/learning.py:40–42,163–173`；`docs/V5E_IMPLEMENTATION.md:223`；第3.4节主键。

3. **B/C判定必须明确on_messages、observe、sleep_interrupts。** 当前intent包含生成式description而没有独立on_question字段；仅on_messages被称selective，observe又明确取消selective语义。需要确定以未过期wake_config条件为准，以及observe是否压过条件。依据：`S/judge_runtime.py:90–119`。

4. **directed跳过C后，one-shot如何消费尚未覆盖。** 当前明确调用可能同时满足所选sender/条件，但只有judge.fulfills_intent才消费；B directed没有语义判定，不能无条件清等待，也不能假称满足。建议编排者明确B默认fulfills=false是否为预期。依据：`S/db/judge.py:209,217–221`；`S/waiting.py:56–77`；设计`444`。

5. **当前directed有文本substring兜底。** `handle in text.lower()`可能把引用、普通文本或更长handle中的目标子串当directed；§5.1说“平台事实”是否仍接受这条兜底需决定。entity offset还按Python字符串切片，Telegram offset是UTF-16；当前substring兜底掩盖部分差异。依据：`nanobot/channels/telegram/runtime.py:2113–2136`。

6. **新增directed/conversation reason会影响多处状态机。** 目前reason枚举/RANK只有judge/proactive/wait_reply/wait_messages/timeout；defer/wait取消例外、messages候选查询写死reason='judge'。若只改schedule调用reason，会破坏“新呼叫在wait期间存活”、已有候选拾取及排序。依据：`S/db/wakes.py:40–49,185–186,392–405`。

7. **120秒恢复口径未明确。** 入站按平台at，batch TTL按received_at，wake又受batch.expires截断。内存化后若只保留普通schedule默认now+120，会改变现有有效期；若按at重建又可能丢弃原本received_at TTL内批次。依据：`S/runtime.py:222`；`S/judge_runtime.py:234–255`；`S/db/judge.py:218–221`；`S/db/wakes.py:217–223`。

8. **内存化不能只删SQL状态。** scheduler deadline、learner全局busy、proactive让位全部依赖pending字段；还要保留pending期间新消息不被旧snapshot吞掉，以及120秒内重启扫描。依据：`S/db/wakes.py:310–318`；`S/expressions.py:283–285`；`S/proactive.py:133,168`；`S/judge_runtime.py:337–345`。

9. **曝光复用需要整批seq及completed turn。** 单trigger_seq不足以证明整批已展示；B1-a允许judge返回前当前turn已结束，所以completed支持是必要行为。依据：`S/db/judge.py:205–211`；`S/db/wakes.py:460–461`；`T/test_social_scheduler.py:553–578`。
